# Fate Collection — аудит, решения и обновление

## Аудит main

Исходная ветка main: `958bc1f`, PR #4. Python 3.12, aiogram 3, SQLAlchemy 2,
asyncpg, PostgreSQL 16+, Alembic. Точка входа main.run, регистрация роутера через
bot.app, экономические операции в infrastructure.game_repository.GameService.
Используются players, wallets, owned_cards, characters, banners, banner_pools,
summons, summon_results, currency_transactions, daily_rewards, image_assets и
render_cache. Новое приложение, ORM или DB-backend не нужны.

У старого релиза 30 персонажей, ×10 за 900, распределение по пяти редкостям и SR+
гарантия. Bootstrap уже сериализован PostgreSQL advisory lock. Операция призыва
блокирует игрока, сохраняет экземпляры и журнал в одной транзакции. Есть уникальный
ключ операции на игрока. PNG отсутствуют в main и рабочем окружении. Вложенные
изображения чата видны визуально, но исходные PNG не доступны как локальные файлы
или downloadable file IDs. Они не заменены JPEG-копиями или сгенерированными артами.

Docker CMD cardlegends и документированная команда Dada Cloud
`alembic upgrade head && exec python -m cardlegends.main` актуальны. Значения
production-переменных не читались, подключение к production-БД не выполнялось.

## Решения и соответствие ТЗ

- Повторно используются кошельки, экземпляры, журнал и транзакции старой схемы.
  Количество копий и first/last obtained вычисляются GROUP BY/min/max по экземплярам;
  отдельная конфликтующая user_collection не создаётся.
- Новый публичный каталог — строго четыре кода AV-F001/F002/F003/L001. Внутренние
  числовые FK 1001–1004 не конфликтуют со старыми ID 1–30. Названия, классы,
  коллекция и пути хранятся в characters. UR хранится как rarity=UR + limited=true,
  отображается как UR Limited; двойная карточка имеет ровно один код и одну запись.
- Новый баннер имеет id=2, code=fate-first-summon. Старый баннер id=1 и его пул
  не меняются. Активный игровой путь выбирает только id=2; старые кнопки не могут
  запустить старое распределение. Уже полученные старые предметы доступны через
  архив и историю; архивные записи не являются дополнительными карточками каталога.
- Seed использует прежнюю transaction advisory lock. Он дополняет четыре записи и
  пул только ими, не обновляет и не удаляет существующие строки. При столкновении
  ID/slug/code с другим содержимым — безопасный отказ без перезаписи. Уже заполненный
  каталог требует только чтения; pool с посторонними ID вызывает отказ. Неактивный
  баннер/персонажи автоматически не включаются обратно.
- Новый draw_fate принимает целые значения 3300/3300/3300/100, проверяет их и выбирает
  интервал через secrets.randbelow(10000). Каждый из десяти розыгрышей независим.
  Legacy draw с SR+ остаётся только для совместимости старого кода/тестов; новый
  GameService его не вызывает. Параметры не зависят от пользователя или времени.
- Новый аккаунт и стартовые 1 000 фиксируются вместе в PostgresPlayerRepository.
  Повторная регистрация обновляет профиль, но не баланс. Старый аккаунт без кошелька
  получает пустой кошелёк, а не повторный стартовый бонус. Существующие балансы,
  транзакции, XP, ежедневные награды и фавориты сохраняются.
- Призыв блокирует players FOR UPDATE в прежнем порядке, проверяет повторы, доступность,
  баланс, лимит частоты и PNG, затем списывает и выдаёт все экземпляры одним commit.
  Новый запрос — не чаще раза в секунду; повтор выполненной операции не блокируется
  cooldown. Нехватка средств и отказ PNG не потребляют случайный результат.
- Уникальны (player_id,key) и (player_id,telegram_update_id). Callback token постоянен
  для показанной кнопки; двойное нажатие/повтор update возвращает старую операцию.
  Проверяется владелец результата/экземпляра и приватный чат. Чужой результат не
  раскрывается. Старые draw-кнопки открывают новый экран без списания.
- total_cost и balance_after сохраняются в операции: повтор показа не подменяет
  исторический баланс текущим и не пересчитывает цену. Доставка выполняется после
  commit. Если Telegram не принял PNG, результат остаётся в истории; можно повторить
  показ. Сбой записи file_id не отменяет уже отправленную карточку.
- ×10 выводит десять строк, количество повторов, стоимость и остаток в одном сообщении;
  до четырёх кнопок открывают PNG. Нет коллажей, серии из десяти сообщений или
  превышения лимита media group/подписи.
- Личная коллекция группирует копии и показывает 0/4–4/4. Неполученные записи закрыты,
  callback просмотра проверяет владение. Общий каталог отдельно позволяет просматривать
  все четыре карточки независимо от коллекции, как требует ТЗ.

## Миграция и права

Создана ревизия `0003_fate_first_summon`, родитель `54b3f0a493e1`:

- characters: nullable code (UNIQUE), card_class, collection_name, image_path;
  limited NOT NULL DEFAULT false для совместимости со старыми строками;
- banners: nullable code (UNIQUE) и JSONB drop_rates;
- summons: nullable total_cost, balance_after, telegram_update_id; уникальность
  player/update, проверки положительной стоимости и неотрицательного баланса;
- индексы summons(player_id,created_at) и owned_cards(player_id,character_id).

Для старых summon стоимость и баланс заполняются из существующей отрицательной
currency_transactions(kind=summon). Если исходного журнала нет, новые поля остаются
NULL; сами исторические результаты/балансы не изменяются. Миграция не создаёт новых
кошельков и не начисляет деньги старым пользователям. Upgrade не удаляет строки и
не меняет старые столбцы. Downgrade этой ревизии удаляет только добавленные метаданные
и индексы, но не предназначен для production-отката с последующим запуском старого
бота: старый seed не знает новых ID. Для production использовать резервную копию
или согласованный forward-fix.

Миграционной роли нужны DDL/владение объектами, доступ к alembic_version, SELECT на
currency_transactions и UPDATE новых столбцов summons для backfill. Успешный DDL
не гарантирует права seed. Инициализатору нужны SELECT/INSERT на franchises,
characters, banners, banner_pools. Дополнительных таблиц/grants для бота нет; прежние
табличные grants распространяются и на добавленные столбцы. Не давать runtime
SUPERUSER или DDL ради seed. Локальный scripts/migrate.py рассчитан на cardlegends_app;
для Dada Cloud администратор подставляет фактическое имя роли.

Проверка под runtime/seed-ролью, без вывода DSN и паролей:

```sql
SELECT current_user;
SELECT t, has_table_privilege(current_user,t,'SELECT') AS can_read,
       has_table_privilege(current_user,t,'INSERT') AS can_seed
FROM unnest(ARRAY['public.franchises','public.characters',
                  'public.banners','public.banner_pools']) AS t;
SELECT version_num FROM alembic_version;
SELECT code, name_en, card_class, rarity, limited
FROM characters WHERE code IN ('AV-F001','AV-F002','AV-F003','AV-L001') ORDER BY id;
SELECT id,code,active,single_cost,ten_cost,drop_rates FROM banners WHERE id=2;
SELECT count(*) FROM banner_pools WHERE banner_id=2;
```

Первому автоматическому startup нужны (выдаёт администратор в нужной БД):

```sql
GRANT USAGE ON SCHEMA public TO bot_role;
GRANT SELECT, INSERT ON public.franchises, public.characters,
  public.banners, public.banner_pools TO bot_role;
```

Остальные runtime-grants перечислены в README. Альтернатива: после миграций отдельно
`python -m cardlegends.cli seed` под DML-ролью, затем запуск с SELECT-only каталогом.
Существующая функция advisory lock должна оставаться доступной роли.

## Исходные файлы и доставка

Точные пути относительно корня репозитория/рабочей директории контейнера:
assets/cards/AV-F001.png, AV-F002.png, AV-F003.png, AV-L001.png.
Файлы не включены: владельцу необходимо добавить доступные ему оригиналы перед
сборкой. Диагностика `python -m cardlegends.cli check-cards` работает без секретов,
БД и Telegram. Она завершится с кодом 1 до готовности всех четырёх статических PNG.

Проверяются формат, целостность PNG, единственный кадр, число пикселей и размер файла.
Для sendPhoto применяются пределы 10 МБ, сумма сторон ≤10000, отношение сторон ≤20.
За пределами photo-лимита оригинал отправляется sendDocument (до 50 МБ); масштабирование
и обрезка не нужны. Кэш зависит от содержимого и метода отправки. Локальный файл
обязателен и при наличии file_id, что позволяет диагностировать потерянный оригинал.
Docker копирует assets, wheel включает assets/cards как package data. Runtime сначала
ищет assets/cards в рабочей директории, затем в исходниках/пакете. Исходные PNG не
меняются, render для Fate копирует файл; внешние art_sources не участвуют в призыве.

## Backup и ручное обновление Dada Cloud

1. Не сливать и не деплоить автоматически. После review оператор добавляет четыре
   оригинальных PNG в указанные пути, запускает check-cards и собирает новый образ.
2. До изменения БД получить проверенную резервную копию. Например, из защищённой
   операторской задачи с настроенными libpq-параметрами/PGSERVICE и PGPASSFILE:

   ```sh
   umask 077
   pg_dump --format=custom --file=animevault-before-fate.dump
   pg_restore --list animevault-before-fate.dump > animevault-backup-contents.txt
   ```

   libpq не принимает postgresql+asyncpg URL напрямую. Не помещать пароль в команду
   и не печатать DATABASE_URL. Сохранить backup вне эфемерного контейнера; проверить
   восстановление на отдельной БД и доступность дампа до начала обновления.
3. Остановить старый polling-процесс. Не оставлять два процесса на один BOT_TOKEN,
   в том числе при rolling deployment. Не удалять postgres_data и не применять
   downgrade либо тесты к production-БД.
4. Применить `alembic upgrade head` под миграционной ролью в той же БД, сохранив
   рабочие TLS-параметры. Alembic читает DATABASE_URL, а не MIGRATION_DATABASE_URL.
5. Проверить права seed и выполнить его отдельной задачей при строгой runtime-роли.
   Либо оставить минимальный INSERT на четыре таблицы для автоматического startup.
6. Оставить прежние BOT_TOKEN, DATABASE_URL, LOG_LEVEL. Если одна роль имеет все права,
   команда остаётся `sh -c 'alembic upgrade head && exec python -m cardlegends.main'`.
   При разделении ролей бот запускается `python -m cardlegends.main` после отдельной
   задачи миграций. Docker CMD cardlegends эквивалентен запуску main.
7. Запустить одну фоновую реплику, без HTTP-порта/нового healthcheck. В логах проверить
   catalog_initialized до polling_starting и отсутствие card_asset_unavailable.
   Секреты и сырые исключения не логируются.
8. Smoke под новым тестовым аккаунтом: дважды /start → 1 000; каталог → ровно четыре
   кода; /rates → 33/33/33/1; ×1 → 900 и оригинальный PNG; повтор той же кнопки → тот
   же результат/баланс; коллекция → одна копия. Для ×10 использовать другой новый
   аккаунт (1 000 → 0, десять результатов). Перезапуск не должен менять баланс/копии.
   У старого аккаунта проверить прежние баланс, XP, архив, фавориты и историю.
9. При временном отказе Telegram повторить показ из истории, не создавать ручной
   компенсирующий summon. При отказе startup смотреть безопасные phase/reason/sqlstate,
   проверить права и PNG; не менять URL/TLS наугад.

## Проверки и ограничения

Автоматизированные проверки включают точные границы 0–9999 и достижимость всех кодов,
симуляцию 200000 выпадений с биномиальным допуском 6σ, десять независимых розыгрышей,
нулевой/повторный бонус, цены, нехватку средств, конкурентное списание и дубли update,
откат после сбоя выдачи, ошибку Telegram после commit, количество копий и прогресс,
защиту личного просмотра, навигацию реального Dispatcher без сети, сохранность
пополненной v0.2 при upgrade/repeat/metadata rollback, повтор seed, блокировку и
раздельные DML-права, готовность/повреждения PNG и fallback устаревшего file_id.

PNG-fixtures в тестах синтетические и не включаются в продукт. Реальные карточки
не проверены на Telegram API, поскольку оригинальных файлов и production-доступа
в сессии нет. До их добавления новые призывы намеренно недоступны; остальные экраны
и сохранённые результаты работают. Фактический deployment в Dada Cloud не выполнялся.
