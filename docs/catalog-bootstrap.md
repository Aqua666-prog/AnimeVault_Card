# Инициализация каталога при первом развёртывании

## Диагноз

Проверен актуальный main `d860316` (слияние PR #3, v0.2.0).
`54b3f0a493e1` создаёт игровые таблицы, но не вставляет данные.
`main.run()` проверял только доступ к players и сразу переходил к Telegram.
`Dockerfile` запускает cardlegends; команда Dada Cloud
`alembic upgrade head && exec python -m cardlegends.main` тоже не вызывает CLI seed.
Единственный путь заполнения был ручной `python -m cardlegends.cli seed`.
Таким образом, успешная миграция и polling совместимы с нулём characters/banners.
`banner_info()` при отсутствии banners.id=1 выдаёт наблюдаемое сообщение.

Это подтверждённая причина в коде, воспроизведённая на отдельной PostgreSQL 16.
Production-БД, её роли, логи и настройки Dada Cloud недоступны в этой сессии;
факт выполнения/невыполнения ручного seed и реальные grants там не проверялись.

Дополнительный дефект конфигурации: старый scripts/migrate.py давал runtime-роли
только SELECT на каталог. Такая роль не могла выполнить первый seed. DDL-привилегии
мигратора и DML-привилегии инициализатора необходимо проверять раздельно.

## Изменение

После database_check, до создания Telegram-клиента, выполняется seed. Все пути
инициализации используют одну PostgreSQL `pg_advisory_xact_lock`, ключ
`0x4156434154414C`. Одновременные startup/CLI сериализуются между процессами.
Ожидание ограничено существующим command timeout (5 секунд); при превышении запуск
завершается безопасно, следующий рестарт повторяет попытку. Блокировка автоматически
снимается при commit/rollback/закрытии соединения. Это блокировка инициализации;
для Telegram по-прежнему необходим только один polling-процесс на токен.

В одной транзакции добавляются недостающие франшизы и 30 персонажей из встроенного
JSON, постоянный баннер id=1 и его пул. Данные не скачиваются из сети.
При ошибке прав или записи откатывается вся инициализация; polling не начинается.
Заполненный каталог проходит только чтение и блокировку, без INSERT/UPDATE/DELETE.
Telegram handlers и middleware seed не вызывают.

Существующие строки не обновляются: кошельки, прогресс, игроки, история, карточки,
арты и их лицензии, параметры/активность/сроки баннера сохраняются. Непустой пул
баннера считается настроенным оператором и сохраняется целиком, даже если в нём
меньше 30 персонажей. Пустой пул наполняется стандартными 30. Отключённых персонажей
или баннер seed не включает заново. При занятом другим персонажем ID/slug возникает
catalog_identity_conflict без изменений БД; автоматическое переименование запрещено.
Новые Alembic-ревизии не нужны: схема не меняется, create_all не используется.

## Обновление Dada Cloud

1. Сохранить резервную копию БД. Дождаться review/merge PR и собрать новый образ
   существующим Dockerfile. Эта работа не выполняет merge или production deploy.
2. Остановить старый polling-процесс перед запуском нового, оставить одну реплику.
   Не удалять БД/volume, не делать downgrade. Существующие DATABASE_URL, BOT_TOKEN
   и TLS-параметры сохранить; не печатать их в терминал/логи.
3. Выполнить `alembic upgrade head` с DATABASE_URL миграционной роли в защищённой
   конфигурации одноразовой задачи. Alembic не выбирает MIGRATION_DATABASE_URL сам.
4. Выбрать права инициализации (см. ниже). Для Dada Cloud использовать реальное имя
   роли, а не запускать scripts/migrate.py вслепую: он рассчитан на cardlegends_app.
5. Запустить `python -m cardlegends.main` под runtime-ролью либо сохранить прежнюю
   shell-команду Alembic+bot, если одна роль имеет оба набора прав. Docker CMD
   `cardlegends` тоже инициализирует каталог. Новый порт/HTTP healthcheck не нужен.
6. Проверить `catalog_initialized` перед `polling_starting`. Первый лог означает,
   что транзакция уже завершена. Он не означает изменения данных при каждом старте.
   При отказе смотреть безопасные phase=catalog_initialization, reason, sqlstate.
   Сырые исключения, SQL, параметры, DSN и токены не выводятся.
7. Проверить `/start` дважды: меню без ошибки баннера, 0/30 для нового игрока,
   стартовая валюта однократно. У старого игрока баланс/коллекция/история прежние.
   Перезапустить процесс и повторить проверку. На ранее настроенном каталоге
   сохраняются его параметры и количество дополнительных персонажей.

## Права ролей

Оператор с правом GRANT выполняет в нужной БД (заменить bot_role на реальную роль,
при необходимости заменить public на используемую схему):

```sql
GRANT USAGE ON SCHEMA public TO bot_role;
GRANT SELECT, INSERT ON public.franchises, public.characters,
    public.banners, public.banner_pools TO bot_role;
```

CONNECT к выбранной БД и остальные игровые runtime grants должны уже существовать
(полный список в README). Для четырёх таблиц не нужны последовательности: ID заданы
явно. Не выдавать SUPERUSER/владение схемой/DDL ради seed. Обычный PostgreSQL 16
разрешает advisory lock без дополнительных грантов; при кастомном отзыве EXECUTE
на этой функции разрешение проверяет администратор БД.

Проверка текущей роли без вывода DSN или паролей:

```sql
SELECT current_user;
SELECT t,
       has_table_privilege(current_user, t, 'SELECT') AS can_read,
       has_table_privilege(current_user, t, 'INSERT') AS can_seed
FROM unnest(ARRAY['public.franchises', 'public.characters',
                  'public.banners', 'public.banner_pools']) AS t;
SELECT count(*) AS characters FROM public.characters;
SELECT id, active FROM public.banners WHERE id = 1;
SELECT count(*) AS pool FROM public.banner_pools WHERE banner_id = 1;
SELECT version_num FROM alembic_version;
```

Альтернатива без INSERT у бота: после миграций выполнить
`python -m cardlegends.cli seed` под отдельной ролью с SELECT/INSERT на четыре
таблицы, используя её DATABASE_URL через защищённую конфигурацию задачи. BOT_TOKEN
для CLI не требуется. Потом запускать бот с исходным runtime URL и SELECT на
каталог. При неполной инициализации бот откажется стартовать до её завершения.
На заполненной БД startup работает и после отзыва INSERT. При намеренном очищении
каталога этот режим требует повторной отдельной инициализации.

## Проверки

Новые интеграционные тесты используют настоящие Alembic и PostgreSQL 16 в отдельной
БД с суффиксом _test: пустая БД, повторный запуск с точным сравнением всех таблиц,
сохранность существующей игры/артов/настроенного баннера/пула, частичный каталог,
конфликт идентичности, три параллельных seed под удерживаемой advisory-блокировкой,
откат после запрета INSERT на banners и успешный повтор без DDL/UPDATE/DELETE,
повтор под ролью только с SELECT. Старт с подставленным Telegram проверяет наличие
30 персонажей/пула до polling и повторный запуск. Unit-тест проверяет отказ до
Telegram и освобождение engine при ошибке seed.

Реальные Telegram API и Dada Cloud при тестировании не используются. Ручная
production-проверка после обновления остаётся за оператором.
