# Диагностика запуска на Dada Cloud

## Что установлено по коду и предоставленным логам

Проверена main на коммите 380e01e952c0b4aaabe8a2e682b272d4a3742dfd. Предоставлены три строки startup_or_polling_failed без JSON-полей и команда:

```sh
sh -c 'alembic upgrade head && exec python -m cardlegends.main'
```

**Точная причина CrashLoop на Dada Cloud не установлена.** Доступа к контейнеру, исходному stderr и настройкам деплоя нет. Ready у PostgreSQL не подтверждает сетевой доступ из приложения, правильные учётные данные, схему или права роли.

Подтверждены следующие особенности и проблемы:

- В исходном main любая обычная ошибка внутри запуска, кроме ConfigurationError, приводит к startup_or_polling_failed и коду выхода 1. Это включает создание engine, подключение и SELECT из players, создание Telegram-клиента, setMyCommands, запуск polling и закрытие ресурсов.
- Исходное сообщение исключения и traceback намеренно скрыты. error_type уже был отдельным JSON-полем, но в тексте event его не было. В присланном выводе JSON-поля отсутствуют. Определить, теряет ли их панель хостинга, обработчик логов или другой образ приложения, по этим строкам невозможно.
- Неуспешная проверка конфигурации даёт другой лог и код 2. Ошибка импорта, отсутствующая команда или неправильная рабочая директория обычно происходят до main и не должны давать этот event.
- В закреплённой версии aiogram ошибки getUpdates перехватываются внутри цикла с backoff. Конфликт двух poller-процессов или webhook обычно даёт повторные ошибки библиотеки, а не немедленный выход через main. Первичный setMyCommands и getMe при входе в polling могут завершить запуск исключением.
- Параметр URL sslmode в исходном коде без преобразования попадает в asyncpg.connect, который такого аргумента не принимает. Эта несовместимость воспроизведена проверкой реальной сигнатуры драйвера. **Наличие sslmode в URL Dada Cloud не подтверждено**, поэтому это не установленная причина данного CrashLoop.
- Dockerfile по умолчанию запускает только cardlegends, без миграций. Локальный Compose запускает отдельный мигратор и ждёт его успеха. Указанная выше команда выполняет миграции перед ботом благодаря && и совместима с Dockerfile проекта. Если именно эта команда фактически запущена и появляется event из main, Alembic перед ним должен был вернуть код 0. Нужно проверить фактическую команду и образ, а не считать миграции отсутствующими.

## Исправления диагностики

В ветке fix/cloud-startup-diagnostics добавлены:

- phase: database_engine, database_check, telegram_client, telegram_commands, telegram_polling; отдельные события миграций и конфигурации;
- error_type и cause_type из цепочки исключений, включая SQLAlchemy orig и asyncpg cause;
- reason, technical_reason и hint из фиксированного списка безопасных причин; SQLSTATE и errno, когда они доступны;
- дублирование безопасных деталей в тексте event для панелей, показывающих только сообщение;
- безопасная классификация исключений в логах aiogram, в том числе повторных конфликтов polling;
- аналогичная диагностика ошибок Alembic и выдачи прав локальной роли приложения;
- преобразование sslmode в ssl с сохранением режима TLS для bot и Alembic. Неверный, повторный sslmode и одновременные ssl/sslmode отклоняются.

Сырые сообщения исключений, traceback, SQL, SQL-параметры, токены и URL не выводятся. Для неизвестной ошибки выводятся класс, этап и категория unexpected_error; её текст не используется как безопасная причина. Сообщение polling_starting означает попытку запуска, а не успешное получение первого update. Закрытие HTTP-сессии и engine сохранено.

Пример безопасного события после исправления:

```text
startup_or_polling_failed phase=database_check error_type=ProgrammingError cause_type=UndefinedTableError sqlstate=42P01 reason=database_schema_missing: PostgreSQL: таблица или представление отсутствует. Действие: Выполните alembic upgrade head в той же БД перед запуском бота.
```

Это пример категории, а не лог Dada Cloud и не утверждение, что там отсутствует таблица.

## Настройки запуска

Собирать существующий Dockerfile из корня проекта. В нём Python 3.12, установка приложения и зависимостей, PATH с /app/.venv/bin и рабочая директория /app. Команда совместима именно с этим образом; при нативной сборке без Docker приложение предварительно должно быть установлено в выбранное Python-окружение.

Окружение:

```env
BOT_TOKEN=replace_with_botfather_token
DATABASE_URL=postgresql+asyncpg://USER:PASSWORD@HOST:PORT/DATABASE
LOG_LEVEL=INFO
```

Префикс postgresql:// автоматически не заменяется: валидатор требует postgresql+asyncpg://. После исправления допустимы ssl=require или sslmode=require; режимы verify-ca/verify-full также сохраняются. Выбор режима и доверенного CA должен соответствовать требованиям провайдера. Исправление не отключает TLS и не ослабляет установленный режим проверки. Другие специфичные параметры libpq автоматически не переводятся.

Если миграции выполняются отдельным шагом деплоя:

```sh
alembic upgrade head
```

Команда запуска бота:

```sh
python -m cardlegends.main
```

Если отдельного шага нет и DATABASE_URL использует роль, имеющую права на миграции:

```sh
sh -c 'alembic upgrade head && exec python -m cardlegends.main'
```

При разделении ролей в отдельном шаге:

```sh
DATABASE_URL="$MIGRATION_DATABASE_URL" alembic upgrade head
```

В основном процессе DATABASE_URL должен остаться URL ограниченной роли бота. Alembic самостоятельно не читает MIGRATION_DATABASE_URL. Мигратору нужны права DDL и работы с alembic_version; боту — CONNECT/USAGE и SELECT/INSERT/UPDATE на players. Нужные роли и права в управляемой БД создаются отдельно. scripts/migrate.py дополнительно требует существующую роль cardlegends_app; для произвольной роли управляемой БД используйте непосредственно Alembic.

Развёртывать как постоянно работающий фоновый процесс с одной репликой. HTTP-сервера и HTTP health endpoint нет. Проверьте, что настройки платформы не требуют открытия PORT или HTTP-ответа. При rolling deployment не допускайте одновременных polling-процессов с одним токеном. Исходящий HTTPS к api.telegram.org должен быть доступен; webhook должен быть отключён отдельно, если раньше использовался. Эти условия требуют проверки в Dada Cloud; в репозитории они не управляются.

## Конкретные проверки после сборки исправленного образа

1. Подтвердить SHA образа/деплоя, рабочую директорию /app и фактическую команду запуска. Файлы alembic.ini и alembic/ должны присутствовать; Python и Alembic должны использовать одно окружение. Проверить оба потока stdout/stderr: приложение пишет JSON в stderr.
2. Проверить результат миграции и код выхода. Выполнить alembic current с той же БД: ожидается 0001_players (head). В SQL-клиенте можно проверить SELECT to_regclass('public.players'); затем права роли приложения на эту таблицу. Сам DSN не публиковать.
3. Скопировать первую полную строку startup_or_polling_failed либо migration_failed с phase/error_type/cause_type/reason/sqlstate/errno. Отдельные JSON-поля не обязательны: безопасные данные есть и внутри event.
4. При database_* проверить доступность endpoint именно из контейнера приложения, порт, DNS, актуальность пароля, название БД, права и TLS. Готовность сервиса БД не заменяет эту проверку.
5. При telegram_unauthorized проверить действительность BOT_TOKEN у BotFather. При telegram_network_error или TLS/DNS-ошибке проверить исходящую сеть. При telegram_conflict проверить другие реплики/локальные процессы и getWebhookInfo. Не вставлять токен в публикуемые команды, URL или логи и не присылать ответ с webhook URL.
6. Проверить код выхода и события завершения контейнера: код 1/2 приложения отличается от остановки по сигналу, OOM или сбоя healthcheck. Для последних нужны события платформы, а не предположение об ошибке Python.

- Проверено отсутствие токена, пароля, полного URL и произвольного текста исключения в диагностическом выводе; категории aiogram сохраняются при скрытии исходных сообщений.

Ни игровая логика, ни схема БД, ни механизм long polling не менялись. Этап 2 не начат.
