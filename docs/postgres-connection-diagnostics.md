# PostgreSQL на Dada Cloud: ConnectionError

## Исходные данные и установленная причина классификации

Проверена main, коммит f42e3a0 (слияние PR #1). Дано: сервис PostgreSQL animevaultcard, порт 5432, статус Ready; приложение animevault-card; переменные BOT_TOKEN, DATABASE_URL и LOG_LEVEL присутствуют, URL начинается с postgresql+asyncpg://. В логе миграции ConnectionError / ConnectionError, reason=unexpected_error, phase=migration_upgrade_or_downgrade.

**Подтверждена ошибка классификации:** базовый встроенный ConnectionError не входил в таблицу безопасных причин, поэтому без распознанного SQLSTATE/errno возвращался unexpected_error. Это не доказывает сбой TLS, DNS или пароля на Dada Cloud. Доступа к этому хостингу, серверным логам и реальному endpoint нет; реальное подключение к нему не проверялось.

Изучен закреплённый asyncpg 0.32.0: он создаёт простой ConnectionError без SQLSTATE, например, когда endpoint отклоняет PostgreSQL SSLRequest, присылает ErrorResponse до TLS или закрывает соединение во время handshake. Такие ошибки могут не оборачиваться SQLAlchemy в DBAPIError. Эти случаи воспроизведены на локальных TCP-имитаторах; они являются возможными причинами, а не установленным диагнозом Dada Cloud.

## Что изменено

- Базовый ConnectionError теперь имеет честную категорию connection_error, если более точная причина недоступна. Неизвестные тексты не выдаются за конкретную сетевую проблему.
- Известные фиксированные сообщения asyncpg сопоставляются с postgres_tls_upgrade_rejected, postgres_ssl_exchange_error, tls_handshake_closed и connection_closed. Переменная часть host:port и исходное сообщение не выводятся.
- ConnectionResetError, ConnectionAbortedError, BrokenPipeError и дополнительные errno распознаются отдельно. Вложенные TLS/DNS/timeout и SQLSTATE имеют приоритет перед общим ConnectionError.
- Добавлен error_origin: последний известный module:function:line из ограниченного списка модулей. Полные пути, исходники, traceback и локальные переменные не выводятся.
- Alembic различает migration_engine, migration_connect и migration_upgrade_or_downgrade. В f42e3a0 фаза migration_upgrade_or_downgrade охватывала и подключение, поэтому прежний лог не позволял отличить транспорт от SQL миграции.
- На этапе подключения логируются db_host_kind (dns/ipv4/ipv6), db_port, db_tls_mode, db_tls_source, таймауты и elapsed_ms. Поля видны и в JSON, и в тексте event. Адрес, имя базы, имя пользователя, пароль, токен и полный DSN не выводятся.
- Добавлена команда проверки через SELECT 1 без Telegram, миграций и изменения данных:

  ```sh
  python -m cardlegends.infrastructure.db_check
  ```

Данные PostgreSQL ErrorResponse, полученные до TLS, не разбираются как доверенные SQLSTATE/сообщения (CVE-2024-10977). Произвольные строки исключений не публикуются. Для нераспознанного ConnectionError дальнейшие серверные логи всё ещё могут быть необходимы.

## Проверка TLS, DNS и таймаутов

SQLAlchemy создаёт асинхронный engine с asyncpg, pool_pre_ping и hide_parameters=True. Параметр sslmode переводится в ssl с сохранением режима; принудительного отключения TLS, смены режима и автоматического обхода проверки сертификатов нет.

Если ssl/sslmode не задан, asyncpg использует PGSSLMODE; при отсутствии этой переменной для TCP применяется prefer. Диагностика показывает источник режима: url, environment или driver_default. Неизвестное значение показывается только как invalid, без его текста. Наличие других PGSSL-переменных, корневого CA и требований провайдера нужно проверять отдельно.

Установка соединения ограничена пятью секундами, включая DNS/TCP/TLS/аутентификацию; command_timeout также пять секунд. Значения не увеличивались и не отключались. socket.gaierror, отказ TCP, недоступность сети, таймаут и ошибка проверки сертификата классифицируются без раскрытия endpoint. Из Ready у PostgreSQL не следует, что имя разрешается и порт доступен именно из контейнера приложения.

## Команда запуска и Dockerfile

Существующий Dockerfile устанавливает проект и зависимости в /app/.venv, добавляет его bin в PATH и задаёт WORKDIR /app. Поэтому команда совместима с этим образом:

```sh
sh -c 'alembic upgrade head && exec python -m cardlegends.main'
```

При ошибке Alembic возвращается ненулевой код и Python-процесс бота не запускается. Это проверено локальным запуском этой точной команды против имитатора, отклоняющего SSLRequest. Миграции не встроены в процесс бота; схема БД, файлы миграций и игровая логика не менялись. Новый Docker-образ и production-деплой в рамках проверки не запускались.

## Действия после слияния PR

1. Пересобрать и развернуть образ из обновлённой main; простой перезапуск старого образа не добавит новую диагностику. Подтвердить новый SHA деплоя и LOG_LEVEL=INFO. У приложения должны быть сетевой доступ к БД и доступ к обоим потокам логов.
2. В секретных настройках сверить host с endpoint сервиса PostgreSQL animevaultcard, порт 5432, фактическое имя базы и учётные данные. Проверить общую приватную сеть/доступность между сервисами. Не публиковать DATABASE_URL.
3. Из того же контейнера и с тем же окружением выполнить python -m cardlegends.infrastructure.db_check. Для неё достаточно DATABASE_URL, BOT_TOKEN не нужен. Код 0 и database_check_succeeded подтверждают подключение и SELECT 1 именно из этого окружения; код 1 означает ошибку подключения/операции, код 2 — конфигурации. Сам по себе успех этой команды не проверяет права DDL или миграции.
4. При успехе оставить указанную команду запуска с Alembic. Проверить успешность миграции, затем запуск polling. По-прежнему нужна одна polling-реплика без обязательного HTTP healthcheck.
5. При ошибке сохранить безопасную строку database_check_failed или migration_failed с phase, reason, error_type, cause_type, error_origin, SQLSTATE/errno, TLS-режимом и elapsed_ms.
6. Если reason=postgres_tls_upgrade_rejected, уточнить у Dada Cloud правильный endpoint/порт и поддержку TLS на нём; выбрать режим согласно требованиям провайдера. Не переключать ssl=disable наугад. При postgres_ssl_exchange_error нужны серверные логи PostgreSQL/прокси на ту же секунду. При tls_handshake_closed/connection_reset проверить TLS-посредник, сетевые правила и завершения соединений на сервере.
7. При dns_resolution_failed проверить имя и сеть из контейнера; при connection_refused — слушающий порт/endpoint; при connection_timeout — сетевую доступность и нагрузку. При connection_error без уточнения использовать error_origin и серверные логи, не объявляя предположение установленной причиной.

## Фактические проверки

- Полный прогон: **105 passed, 55.71 s**, без пропусков (90 модульных и 15 интеграционных тестов).
- Использовались отдельная PostgreSQL 16 и локальные TCP-имитаторы. Подключение к Dada Cloud не выполнялось.
- Реальный asyncpg проверен при отказе SSLRequest, ErrorResponse до TLS, отказе TCP и зависшем SSL-обмене. Проверены категории, отсутствие секретов и безопасный error_origin.
- Точная команда запуска проверена на локальном отказе TLS: Alembic завершился с кодом 1, бот не запускался; лог содержит migration_connect и postgres_tls_upgrade_rejected.
- db_check успешно подключается к тестовой БД без BOT_TOKEN и не меняет число игроков/ревизию схемы. Отказ аутентификации и неверная конфигурация дают безопасные коды/логи.
- Сохранены проверки регистрации, конкурентного upsert, миграций upgrade/downgrade и закрытия ресурсов. Игровые модули и alembic/versions не менялись.
- Ruff lint, format --check и git diff --check прошли. Wheel собран. Новый Docker-образ не собирался; существующий Dockerfile проанализирован.
- Вывод проверен на отсутствие паролей, URL, адресов и произвольных сообщений исключений. Образцы/test-only значения в исходниках не являются секретами.

Секреты в Dada Cloud не читались и не изменялись. PR подготовлен отдельно; слияние и деплой не выполнялись. Этап 2 не начат.
